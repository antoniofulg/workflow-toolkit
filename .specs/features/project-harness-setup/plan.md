# Project harness setup

## Problem

Project rules and installed specialist guidance can disappear when planners derive a feature's criteria. A builder and Verifier can then satisfy an incomplete contract. Antonio reports unnecessary interface copy, incomplete loading states, omitted transitions and inconsistent shared styling. The same omission risk applies to security, data and architecture; frequency and cost are unmeasured.

Setup will discover and refine project requirements with the user, route them on demand, and carry them through independent criteria review and implementation verification.

## Flow

Reuse WTK's existing context budget, construction constraints, phase artifacts, security procedure, proportional validation and execution-selection contract.

1. `wtk` (exists) routes an explicit setup/review/update request to `wtk-setup` (door 1).
2. `wtk-setup` discovers actual guidance and available skills, interviews about unresolved rules and driver responsibilities, then proposes or applies the authorized project-guidance delta (door 1).
3. Lean Plan/Checks and modular Plan/Implement (exist) load the shared project-requirements reference and land applicable adopted requirements in their native artifacts (door 2).
4. The coordinator uses one fresh non-author criteria reviewer before dependent feature build; existing Plan/Checks review may supply that responsibility (door 2).
5. Lean and modular Verify (exist) independently derive applicability from the actual delta and reconcile project rules, criteria and implementation (door 2).
6. The existing distribution contract exposes the new skill, portable references, manifest entry and Claude alias together (door 1).

## Impact

| Front | What changes |
| --- | --- |
| public skill catalog | Add `wtk-setup`; update the complete install list, manifest, alias and canonical distribution expectations from 12 to 13 skills |
| project guidance | Explicit setup may create/update project-owned instructions; installation continues to leave the harness untouched |
| feature workflow | Both planning paths inherit applicable requirements and use one fresh criteria reviewer before feature build |
| verification | Both Verify procedures independently challenge applicability and omission under every profile |
| stored data | No runtime schema, migration, new policy registry or native role configuration |

## Relations

None - no stored-data shape change.

## Surface

None - no HTTP route or executable CLI signature changes. The public `wtk-setup` skill name and its proposed, unresolved and applied conversational dispositions are covered by Landing door 1 and Observable.

## Landing

| One-way door | Literal shape | Alternative rejected |
| --- | --- | --- |
| 1. New distributed skill | `wtk-setup`, included in the complete WTK set with portable references | External frontend-specific setup - cannot own generic project policies and both WTK planning paths |
| 2. Feature requirements contract | One shared conditional reference; one fresh feature criteria reviewer and independent applicability checks under every verification profile | Planner-selected source list as complete - reviewers can inherit the same omission |

## Criteria

### S1: Harness discovery and project guidance (P1)

**Acceptance Criteria**

1. WHEN setup inspects a new or existing project THEN it SHALL propose a small relevant baseline and interview about unresolved policy expectations and driver-skill responsibilities across relevant areas, including security.
2. WHEN setup discovers skills THEN it SHALL inspect actual available metadata, distinguish adopted bindings from proposals, and identify policy, expertise and proof-capability gaps separately without automatic installation.
3. WHEN evidence conflicts or a required source/driver is unavailable THEN setup SHALL name the affected requirement and use existing open, blocks or blocks go-live dispositions rather than silently substituting authority.
4. WHEN project guidance is adopted during authorized setup THEN it SHALL have a trigger, one owning source, observable outcome and evidence approach, with root instructions limited to routing and authority and conditional reads selected by role, phase and affected concern without hiding cross-cutting obligations.
5. WHEN setup chooses a guideline location THEN it SHALL reuse existing project owners and conventions or propose `docs/guidelines/` when none exists, allowing a user-chosen alternative and creating only applicable documents.
6. WHEN setup is rerun THEN it SHALL preserve equivalent decisions and repair or retire stale bindings within authority after input changes, asking only about materially unsettled responsibilities.
7. WHILE the request is assessment-only setup SHALL provide findings and a proposed delta without modifying the consuming harness.

**Independent test:** Inspect skill behavior using new-project and existing-project scenarios; preserve assessment sentinels and compare instructions with the binding design.

### S2: Requirement inheritance and independent checking (P1)

**Acceptance Criteria**

8. WHEN Lean or modular planning derives feature criteria THEN it SHALL read applicable project guidance and selected required driver instructions, landing adopted requirements in concrete criteria/checks, evidenced existing behavior, justified non-applicability or a classified unresolved gap.
9. WHEN a feature contract is ready for dependent build THEN one fresh non-author reviewer SHALL independently derive concerns and sources from the request, proposed delta and authoritative routing, challenge exclusions and return missing requirements before build; extra specialists require a concrete gap.
10. WHEN criteria review produces findings THEN the planner SHALL correct the owning contract and the reviewer SHALL recheck affected coverage and blocking dispositions using the existing Plan/Checks review where suitable.
11. WHEN the project adopts content-shaped loading THEN its feature criteria SHALL identify retained known content, unresolved masks derived from loaded composition, action/refresh behavior and pending/ready geometry, wrapping and overflow evidence at relevant widths and response conditions.
12. WHEN either Verifier checks a feature THEN it SHALL independently derive applicability from the request, actual delta and authoritative routing, report omitted sources or requirements despite green listed proofs, and require evidence that reaches each claimed boundary.
13. IF evidence is unavailable or an implementation violates an adopted rule THEN the Verifier SHALL retain the obligation as unproven or failed and return fixes to the builder using existing remediation limits.
14. WHEN work resumes or relevant sources/concerns change THEN its handoff and affected coverage SHALL be reconciled while valid unchanged evidence is retained; bounded maintenance SHALL retain its direct proportional route.

**Independent test:** Challenge a plan that omits an entire security guideline and a criterion, then challenge a nominally green implementation with content-shaped-loading violations; verify that scope is independently rediscovered.

### S3: Portable distribution (P1)

**Acceptance Criteria**

15. WHEN the full WTK set is discovered or packaged THEN it SHALL contain 13 skills including `wtk-setup`, consistent manifest and tracked Claude alias entries, and resolvable installed references without optional companions.
16. WHILE the skill package is installed the existing harness-preservation contract SHALL remain in force; setup SHALL add no executable installer, policy registry, mandatory native agent files or application runtime dependency.

**Independent test:** Run the owning distribution suite, including isolated discovery and harness-preservation checks.

## Out of scope

| Excluded | Why |
| --- | --- |
| Consuming application changes, deployment and production actions | These projects are read-only evidence inputs; this task changes the WTK source pack |
| New validators, policy schemas, agent presets and installer executables | Existing documentation, distribution checks and host dispatch mechanisms own those responsibilities |
| Full behavioral reliability or commercial claims | Bounded source review and scenario probes cannot certify universal model behavior |
